# Postal mail server on k3s — design

Date: 2026-08-04
Branch: feat/openvpn-runner-image

## Goal

Self-hosted SES replacement: Postal on the k3s cluster serving the mail
domain **mail.biyard.co**, with

- **outbound**: direct delivery from the home IP (outbound port 25
  verified open; deliverability caveats accepted),
- **inbound**: MX → Postal → HTTP webhook → Redpanda topic
  `postal.inbound` (SES+Lambda pattern replacement).

## Decisions (from brainstorming)

- Mail domain: `mail.biyard.co` (addresses `*@mail.biyard.co`).
- Outbound: direct send first; add a relay later only if deliverability
  actually hurts.
- Inbound handling: events onto Redpanda (not mailboxes, not forwarding).
- Local charts (repo convention), not community Helm charts.

## Architecture

All in namespace `infra`, added to `k8s/helmfile.yaml`.

### Chart `k8s/charts/postal`

- **MariaDB** Deployment + PVC (local-path). Postal requires MySQL-family
  DB (cannot reuse pg-stack). Postal v3 needs no RabbitMQ.
- **postal-web** — `ghcr.io/postalserver/postal:3.x` (public image, pulled
  directly; no local import needed), `postal web-server`, Service :5000,
  Ingress `postal.dev.biyard.co` + existing `dev-biyard-co-tls` wildcard.
  Postal has its own login → no basic-auth annotation.
- **postal-smtp** — `postal smtp-server`, **hostPort 25** pinned to
  `lima-k3s-server` (same pattern as openvpn hostPort 1194). Handles both
  inbound reception and is the HELO identity `mail.biyard.co`.
- **postal-worker** — queue processing, actual outbound delivery.
- **postal.yml** ConfigMap; **signing key** RSA Secret created
  imperatively (like `console-basic-auth`; must be recreated on fresh
  bootstrap — documented).
- **init Job** — `postal initialize` (DB schema). Admin user via one-time
  `kubectl exec … postal make-user` (interactive; documented, not
  automated).

### Chart `k8s/charts/mail-bridge`

Redpanda Connect (single binary) Deployment + ConfigMap pipeline:

- input `http_server` :4195 path `/inbound`
- output kafka → `redpanda-0.redpanda.infra.svc.cluster.local:9093`,
  topic `postal.inbound`

Postal route for `*@mail.biyard.co` → HTTP endpoint
`http://mail-bridge.infra.svc:4195/inbound`. Postal org/server/domain/
route setup is one-time manual via web UI (documented in
`k8s/README-mail.md`).

### External paths

- **Inbound**: router adds **TCP 25 → 192.168.0.54** forwarding (manual
  user step, same as 80/443/1194).
- **Outbound**: pods egress with the home public IP (121.131.101.30
  as of writing).

### DNS (Route53, biyard.co zone)

| record | type | value |
|---|---|---|
| mail.biyard.co | A | home public IP (121.131.101.30) |
| mail.biyard.co | MX | `10 mail.biyard.co` |
| mail.biyard.co | TXT | `v=spf1 a mx ~all` |
| _dmarc.mail.biyard.co | TXT | `v=DMARC1; p=none;` |
| postal-*._domainkey.mail.biyard.co | TXT | DKIM value generated by Postal after domain registration |
| rp.mail.biyard.co | A + MX + SPF | return-path domain (per Postal UI instructions) |

Records applied with the cluster's existing Route53 credentials if the
IAM policy allows; otherwise the record list is handed to the user.
MX target must be an A record (no CNAME) → **home IP change requires a
manual A-record update** (iptime DDNS not usable as MX target).

## Accepted limitations

- No PTR record on a residential IP → large receivers may spam-folder or
  reject direct outbound. Mitigation deferred (relay can be added later
  in Postal config without redesign).
- Single node, single instance: mail reception pauses when the lima VM is
  down (senders retry for days; loss unlikely).

## Verification

- Outbound: send from Postal (web UI / SMTP credential) to a Gmail
  address; confirm arrival (spam folder counts as arrival).
- Inbound: send from Gmail to `test@mail.biyard.co`; confirm the event in
  Redpanda: `rpk topic consume postal.inbound`.
- DKIM/SPF: check Authentication-Results headers on the Gmail side.
